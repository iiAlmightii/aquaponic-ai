SECTION 1 — PROJECT OVERVIEW
================================================================================

1.1 PROBLEM STATEMENT
----------------------
Aquaponic and land farming in India suffers from three interconnected problems:

  a) INFORMATION ASYMMETRY: Small and marginal farmers (~86% of India's farming
     community) lack access to structured financial planning tools tailored to
     their specific production systems. They make investment decisions based on
     intuition, not data.

  b) VOICE/LANGUAGE BARRIER: Most farm advisory tools require typing on a
     keyboard or navigating complex UIs. Rural farmers are more comfortable with
     voice interaction but existing tools do not handle agricultural domain
     vocabulary well (STT systems confuse "tilapia" with "telepathy", "NFT" with
     "empty", etc.).

  c) NO INTEGRATED INTELLIGENCE: Existing tools treat financial planning, water
     quality monitoring, crop selection, and market prices as completely separate
     problems. Farmers have to consult multiple systems, none of which understand
     the relationships between these data domains.

1.2 OBJECTIVE
--------------
To build a unified, voice-first, AI-driven farm management platform that:
  1. Guides farmers through structured surveys via voice or text
  2. Automatically computes financial projections (CAPEX, OPEX, ROI, NPV, IRR)
     with three scenario analyses (pessimistic/base/optimistic)
  3. Recommends crop choices based on water parameters, area, and system type
  4. Ingests real-time IoT water quality data (pH, DO, temperature, ammonia)
  5. Generates downloadable PDF financial reports
  6. Provides conversational AI advice via a domain-specialized LLM (Sarvam 30B)
  7. Synchronizes financial data to Google Sheets for offline farmer access
  8. Supports BOTH aquaponic farms AND conventional land farms (dual survey path)
  9. Provides analytics dashboards for aggregate insight across sessions

1.3 WHY THIS PROJECT WAS BUILT
--------------------------------
India has ~100,000+ aquaponic setups and millions of land farmers but:
  - No free, localized financial planning tool exists for aquaponics
  - NABARD and government subsidy calculations require structured CAPEX/OPEX data
    that farmers cannot easily compile
  - Academic research shows >60% of small aquaponic ventures fail in Year 1 due
    to cash-flow mismanagement, not technical problems
  - The project directly addresses UN SDG 2 (Zero Hunger) and SDG 8 (Economic
    Growth) by making agricultural intelligence accessible to resource-constrained
    farmers

1.4 REAL-WORLD SIGNIFICANCE
-----------------------------
  - A farmer in Maharashtra with a 50 m² aquaponic setup can complete the
    10-minute voice survey in Marathi-accented English and immediately receive
    a PDF showing that their feed costs are 48% of OPEX (above the safe 35%
    threshold), their payback period is 18 months, and their ROI is 31%.
  - This same report can be submitted to a bank for a NABARD KCC loan.
  - The Land Farm variant supports conventional crop farmers who want to
    evaluate which crops to grow based on market prices and soil conditions.
  - The platform is designed for deployment at Krishi Vigyan Kendras (KVKs),
    NGOs working with farmer cooperatives, and agricultural universities.

MODULE 1: AUTHENTICATION MODULE
---------------------------------
File: backend/routers/auth.py, backend/services/auth_service.py
Models: models.User

PURPOSE:
  Secure user registration, login, and token-based session management.
  Ensures all farm data is isolated per user.

INPUT:
  - Registration: email, full_name, password (plain text)
  - Login: email, password

PROCESSING LOGIC:
  - bcrypt hashes password on registration (salted, 10+ rounds)
  - On login, bcrypt.verify() checks password against stored hash
  - On success, generates two JWTs:
      * access_token  (HS256, expires in 60 minutes)
      * refresh_token (HS256, expires in 7 days)
  - All subsequent API calls require Bearer token in Authorization header
  - FastAPI dependency `get_current_user` decodes JWT and returns User object
  - Rate limit: 10 requests/minute on auth endpoints (slowapi)

OUTPUT:
  - access_token, refresh_token, token_type

INTERACTION WITH OTHER MODULES:
  - Every router uses `Depends(get_current_user)` to enforce authentication
  - user.id is used as FK for Farm, Session, FinancialPlan records

WHY NECESSARY:
  - Multi-tenant system — farmer A must not see farmer B's data
  - JWT is stateless, scales horizontally without sticky sessions
  - Redis stores session cache (TTL 3600s) to reduce DB lookups

TECHNOLOGIES: FastAPI, python-jose (JWT), passlib/bcrypt, SQLAlchemy, slowapi


MODULE 2: QUESTIONNAIRE ENGINE
--------------------------------
File: backend/services/questionnaire_engine.py
Class: QuestionnaireEngine

PURPOSE:
  The core survey brain. Drives a structured 26-question interview about the
  farm covering: setup, fish data, crop data, water quality, financials, goals.

INPUT:
  - session.context_data (JSON dict): {"answered": [...], "answers": {...}}
  - Raw answer text (string from voice or keyboard)

PROCESSING LOGIC:
  1. get_next_question(context):
     - Iterates QUESTION_BANK in order
     - Skips already-answered questions
     - Evaluates skip-logic conditions (e.g., skip water_ph if has_iot_sensors=True)
     - Returns next unanswered Question object (or None if complete)

  2. parse_answer(question, raw_answer):
     - NUMBER type: regex extracts digits; word-to-number converter handles spoken
       inputs ("fifty" → 50, "two lakh" → 200000); unit normalization (grams → kg)
     - BOOLEAN: fuzzy yes/no matching (handles "yeah", "yep", "nah")
     - SELECT: substring fuzzy matching against options list
     - MULTISELECT: matches multiple options from free-form text
     - TEXT/farm_location: validates City, State format; recognizes all 36 Indian
       states/UTs; strips voice prefix phrases ("I am located in...")

  3. record_answer(context, question, parsed_value):
     - Appends question.id to context["answered"]
     - Stores parsed_value in context["answers"][question.id]

  4. is_complete(context):
     - Returns True when get_next_question() returns None

SKIP LOGIC EXAMPLE:
  - Question "water_ph" has follow_up_condition: {"if": "has_iot_sensors == false"}
  - If farmer answered "yes" to IoT sensors, pH question is skipped (IoT provides it)

OUTPUT:
  - Next Question object with id, text, type, options, unit, hint
  - Progress tuple (answered_count, total_questions)

INTERACTION:
  - Called by session router on every POST /session/answer
  - On completion, triggers CropIntelligenceService.evaluate_session()
  - Extracted answers feed into FinancialService.create_plan()

TECHNOLOGIES: Python dataclasses, Enum, regex, no DB dependency (pure logic)


MODULE 3: VOICE/STT MODULE
----------------------------
File: backend/routers/audio.py, backend/services/voice_interpretation.py
Frontend: frontend/src/app/hooks/useVoiceRecorder.js

PURPOSE:
  Convert farmer's voice input to text, clean it, and extract structured data.
  This is the most complex module due to agricultural domain vocabulary challenges.

INPUT:
  - Audio file upload (WebM/WAV/MP3/M4A/OGG)
  - Optional: language code, question_context (prompt hint), question_id, question_type

PROCESSING LOGIC:
  BACKEND (audio.py):
  1. File received as UploadFile, written to temp file
  2. faster-whisper model loaded lazily and cached (lazy singleton pattern)
  3. DUAL ATTEMPT strategy:
     Attempt A: beam_size=5, VAD filter ON, full context prompt
     Attempt B (only for farm_name with low confidence): beam_size=1, no VAD,
                targeted prompt "output only the farm/project name"
  4. Better attempt selected by comparing stt_confidence values
  5. Confidence calculated from segment avg_logprob (log probability → exp → 0..1)
     multiplied by (1 - no_speech_prob)
  6. Post-processing (voice_interpretation.py):
     - FILLER REMOVAL: removes "um", "uh", "like", "you know", etc.
     - DOMAIN NORMALIZATION: fixes STT errors specific to aquaponics vocab:
         "talapia/tilapiya/telepathy" → "tilapia"
         "kaarp/carf/cap"            → "carp"
         "nft/empty/an empty/n f t"  → "nft"
         "dwc/do you see"            → "dwc"
     - NUMBER NORMALIZATION: "for" → "4", "two hundred fifty" → "250"
       (for number-type questions, voiced integers are converted to digits)
  7. For farm_name questions: extract_farm_name_candidates() runs an n-gram
     candidate scoring algorithm (heuristic: proper noun score + Farm/Project hint
     bonus + length penalty) returning best name + 2 alternatives + confidence
  8. Audit log appended to JSONL file for debugging/evaluation

  FRONTEND (useVoiceRecorder.js):
  - Uses Web Speech API (browser native) as primary OR
  - Falls back to MediaRecorder API → POST /api/v1/audio/transcribe
  - Sends audio chunk with question_id and question_type for context-aware decoding

OUTPUT:
  TranscribeResponse {
    text: string (cleaned transcript),
    confidence: float (0..1),
    provider: "faster-whisper",
    audit_id: string (UUID for traceability),
    interpretation: {farm_name: {best, alternatives, confidence, needs_confirmation}},
    alternatives: string[],
    confidence_details: {segments, avg_logprob, avg_no_speech_prob}
  }

WHY NECESSARY:
  - Text keyboards are a barrier for field use; voice lowers data entry friction
  - Domain-specific STT normalization is critical — generic Whisper output is
    unusable for aquaponics terms without post-processing
  - The dual-attempt strategy improves farm name accuracy significantly
  - Audit trail enables WER (Word Error Rate) evaluation for model comparison

TECHNOLOGIES:
  - faster-whisper (CTranslate2 quantized Whisper large-v3) — CPU/CUDA
  - Web Speech API (browser-native STT fallback)
  - Python regex, JSONL audit logs
  - Device: CPU (int8 quantization) or GPU (float16) configurable via env var


MODULE 4: SESSION LIFECYCLE MODULE
------------------------------------
File: backend/routers/session.py
Models: models.Session, models.SessionAnswer

PURPOSE:
  Manages the stateful questionnaire session. Stores progress, enables back
  navigation, and transitions session to "completed" state.

KEY ENDPOINTS:
  POST /session/start  → creates Session record, returns Question 1
  POST /session/answer → validates answer, stores SessionAnswer, returns next Q
  POST /session/back   → rolls back last answer (enables correction)
  GET  /session/{id}   → returns current session state
  DELETE /session/{id} → marks session "abandoned"

PROCESSING LOGIC:
  - context_data (JSONB) accumulates all answers; deep-copied before mutation
    so SQLAlchemy dirty-detection fires correctly
  - On completion: CropIntelligenceService.evaluate_session() runs synchronously
    and attaches results to context_data["crop_intelligence"]
  - Back navigation: pops last question_id from context["answered"], moves its
    value to context["draft_answers"] (so UI can pre-fill the field), deletes
    latest SessionAnswer row from DB

STATE MACHINE:
  in_progress → completed (all questions answered)
  in_progress → abandoned (user explicitly quits)
  completed   → in_progress (back navigation re-opens)

TECHNOLOGIES: FastAPI, SQLAlchemy async, Pydantic, PostgreSQL JSONB


MODULE 5: FINANCIAL CALCULATION MODULE
----------------------------------------
File: backend/services/financial_service.py
Classes: FinancialInputs, FinancialCalculator, FinancialService

PURPOSE:
  The mathematical core. Converts survey answers into actionable financial
  projections. Fully deterministic — no AI, no randomness.

INPUT: FinancialInputs dataclass
  Capital:  infrastructure_cost, equipment_cost, initial_stock_cost
  Monthly:  feed, labor, utilities, maintenance, other_cost
  Revenue:  fish_revenue, crop_revenue, other_revenue
  Config:   land_area_sqm, horizon_months, discount_rate_annual (8%)

PROCESSING LOGIC (FinancialCalculator.compute):
  1. Applies scenario_factor to monthly revenue:
     - Base: 1.0 (no change)
     - Pessimistic: 0.75 (-25% revenue shock)
     - Optimistic: 1.30 (+30% revenue uplift)

  2. Derived metrics:
     - total_capex = infra + equipment + stock
     - annual_opex = monthly_opex × 12
     - annual_revenue = adj_monthly_rev × 12
     - gross_profit = annual_revenue - annual_opex
     - ROI = net_profit / capex × 100
     - payback_months = capex / monthly_net
     - break_even_month: first month cumulative cash flow ≥ 0
     - per_sqm metrics: revenue/profit/capex/opex per m²
     - revenue concentration: fish vs crop vs other share %
     - cost concentration: feed vs labor vs utilities vs maintenance %

  3. Monthly cash flow array (length = horizon_months):
     Each entry: {month, revenue, opex, net, cumulative}
     Month 1 subtracts full CAPEX from cumulative

  4. NPV calculation (Discounted Cash Flow):
     NPV = -CAPEX + Σ(monthly_net / (1 + r)^m)  for m in 1..horizon
     r = monthly_discount_rate = (1 + 0.08)^(1/12) - 1 ≈ 0.6434%

  5. IRR approximation (bisection search, 200 iterations):
     Find monthly IRR such that NPV = 0
     Annualized: IRR_annual = (1 + monthly_IRR)^12 - 1

  6. Rule-based recommendations (15+ rules):
     - Cash flow negative → "Operation is cash-flow negative"
     - Feed cost > 45% OPEX → bulk purchasing + FCR tracking advice
     - Labor > 45% OPEX → automation suggestions (feeders, timers)
     - Utilities > 25% OPEX → energy efficiency + solar advice
     - Payback > 48 months → NABARD subsidy exploration
     - Fish revenue > 85% → revenue concentration risk warning
     - ROI > 30% AND payback < 24 months → scaling opportunity

FinancialService.create_plan():
  - Runs compute() for base, pessimistic, optimistic
  - Calls _generate_recommendations()
  - Persists FinancialPlan to DB with all three scenario JSONs

OUTPUT: FinancialMetrics (30+ computed fields) + scenarios dict + recommendations

TECHNOLOGIES: Python dataclasses, math (bisection), SQLAlchemy async


MODULE 6: LAND FARM SURVEY MODULE
-----------------------------------
File: backend/services/land_farm_survey_engine.py,
      backend/services/land_financial_service.py,
      backend/routers/land_survey.py

PURPOSE:
  Separate survey path for conventional land farmers (not aquaponic).
  Handles crop-centric data: multiple crop types, area allocation, market prices,

KEY DIFFERENCES from Aquaponic Survey:

  - Integrates land_market_price_service for live/cached commodity prices

  - Per-crop: revenue = yield_kg × market_price_per_kg × cycles_per_year
  - Total cost: input_cost + labor_cost + irrigation_cost + other_cost
  - ROI = profit / total_cost × 100
  - Outputs per-crop performance table + aggregate summary

TECHNOLOGIES: Python, regex, same FastAPI/SQLAlchemy stack


MODULE 7: CROP INTELLIGENCE MODULE
------------------------------------
File: backend/services/crop_intelligence_service.py
Data: backend/data/crop_knowledge_base.json

PURPOSE:
  Rule-based (no LLM) feasibility engine. Evaluates whether a specific crop
  is viable given the farmer's system conditions.

INPUT:
  - crop_name, area_m2
  - Optional: temperature_c, pH, system_type

PROCESSING LOGIC:
  1. Loads crop knowledge base (JSON) once into memory (singleton pattern)
  2. For each crop, checks four thresholds:
     AREA: area < min_area_m2 → "not_feasible"
           area < optimal_area_m2 → "challenging"
     TEMPERATURE: outside [t_min, t_max] range → warning
     pH: outside [ph_min, ph_max] range → warning
     SYSTEM TYPE: checks compatibility list (NFT, DWC, media_bed, raft)
  3. Yield projection: yield_per_m2 × area × cycles_per_year
  4. suggest_crops(): evaluates all crops in KB, sorts by feasibility
  5. evaluate_session(): called automatically at session completion;
     reads crop_types and farm_area_sqm from context["answers"]

OUTPUT:
  {
    feasibility: "feasible" | "challenging" | "not_feasible" | "unknown",
    reasons: [...],
    warnings: [...],
    crop_data: {growth_days, cycles_per_year, yield_per_m2, ...},
    yield_estimate: {area_m2, annual_yield_kg, ...}
  }

WHY NO LLM HERE:
  Crop physiology thresholds are well-established in FAO literature (FAO 589,
  ICAR-CIFA, UVI crop valuation studies). Rule-based is 100% deterministic,
  zero API cost, zero latency, and auditable. LLMs introduce hallucination risk
  for factual thresholds.

TECHNOLOGIES: Python, JSON knowledge base, no external dependencies

MODULE 13: STT EVALUATION MODULE
----------------------------------
File: backend/eval/run_wer_eval.py, backend/routers/eval.py
       (only active when EVAL_MODE=true)

PURPOSE:
  Offline Word Error Rate (WER) evaluation framework for comparing STT
  providers (faster-whisper vs browser Web Speech API).

PROCESSING:
  - Runs test audio files through /api/v1/audio/transcribe
  - Computes WER = (S + D + I) / N where S=substitutions, D=deletions,
    I=insertions, N=total reference words (classic Levenshtein-based metric)
  - A/B test design: same audio tested with both providers

WHY THIS EXISTS:
  Validates that faster-whisper on CPU with domain normalization actually
  outperforms browser-native STT for aquaponics terminology.

SECTION 4 — SYSTEM ARCHITECTURE

4.1 OVERALL ARCHITECTURE (Three-Tier)
----------------------------------------
  TIER 1 — PRESENTATION:
    React 18 (Vite) + TypeScript
    State: Zustand global store
    API calls: Axios with JWT interceptor (api.js)
    Voice: Web Speech API / MediaRecorder → faster-whisper
    UI: shadcn/ui components, TailwindCSS, Recharts for charts
    Build: Vite → static files → served by Nginx

4.2 COMPLETE DATA FLOW (Voice Survey → PDF)
---------------------------------------------
  Step 1: User speaks into microphone
          → MediaRecorder captures WebM audio
          → POST /api/v1/audio/transcribe (multipart/form-data)

  Step 2: Backend writes audio to temp file
          → faster-whisper model transcribes (beam_size=5, VAD filter)
          → Confidence calculated from avg_logprob
          → Domain normalization: FILLER_NOISE_RE + DOMAIN_REPLACEMENTS
          → Number normalization (if question_type=number)
          → Farm name entity extraction (if question_id=farm_name)
          → Response: {text, confidence, alternatives, audit_id}
          → Temp file deleted (finally block)

  Step 3: Frontend shows transcript in input field
          → User confirms or edits
          → POST /api/v1/session/answer {session_id, question_id, answer_text}

  Step 4: QuestionnaireEngine.parse_answer() validates and structures answer
          → SessionAnswer row created in DB
          → context_data updated (deep copy before mutation)
          → Next question returned OR completion signal

  Step 5: On completion:
          → CropIntelligenceService.evaluate_session() runs
          → Results written to context_data["crop_intelligence"]
          → Session.status = "completed"

  Step 6: User clicks "Download Report"
          → GET /api/v1/report/{session_id}
          → FinancialService.create_plan() runs (3 scenarios)
          → ReportLab generates PDF in memory
          → StreamingResponse returns PDF bytes with Content-Disposition header

SECTION 5 — TECHNICAL DEEP DIVE

5.1 FINANCIAL ALGORITHMS
--------------------------

NET PRESENT VALUE (NPV):
  Formula: NPV = -CAPEX + Σ [monthly_net / (1 + r)^m]  for m=1 to horizon
  r = (1 + 0.08)^(1/12) - 1  (monthly equivalent of 8% annual discount rate)
  Interpretation: NPV > 0 means the investment is profitable in today's money.
  If NPV < 0 and no break-even within horizon → "project does not break even"
  recommendation fires.

INTERNAL RATE OF RETURN (IRR):
  No closed-form solution → bisection search (200 iterations, tolerance 0.01)
  lo=-0.999, hi=10.0 (monthly IRR bounds)
  At each iteration: compute NPV at midpoint; narrow interval based on sign
  Annualized: IRR_annual = (1 + monthly_IRR)^12 - 1
  WHY BISECTION: Newton-Raphson requires derivative; bisection is simpler and
  guaranteed to converge for monotone NPV function.

ROI:
  Simple ROI = net_profit_annual / total_capex × 100
  (Year 1 only; not risk-adjusted)
  Why not CAGR? ROI is the most universally understood metric by rural farmers
  and bank loan officers in India.

SCENARIO ANALYSIS:
  Pessimistic: 0.75 factor on revenue (simulates 25% demand/price drop)
  Optimistic: 1.30 factor on revenue (simulates channel diversification uplift)
  Base: 1.0
  Why these factors? Based on typical aquaponic farm income volatility in
  literature. A tilapia price crash of 20-25% occurred in Maharashtra 2022.

5.2 STT CONFIDENCE CALCULATION
---------------------------------
  faster-whisper outputs per-segment avg_logprob (negative log probability):
    avg_logprob ≈ -0.2 → high confidence (exp(-0.2) ≈ 0.82)
    avg_logprob ≈ -1.0 → low confidence (exp(-1.0) ≈ 0.37)
  Multiplied by (1 - no_speech_prob) to penalize silence-only segments
  Final confidence = mean across all segments, clamped to [0, 1]

  DUAL ATTEMPT RATIONALE:
  First pass: VAD filter ON removes silence, beam_size=5 for accuracy
  Second pass (farm names only): VAD OFF keeps full audio; beam_size=1 reduces
  hallucination; tuned prompt reduces extra words
  If second pass confidence > first → use second

5.3 ASYNC ARCHITECTURE
------------------------
  All FastAPI endpoints are async def using await for all DB and network calls
  asyncio.gather() in report.py runs 4 DB queries in parallel (no sequential
  waterfall), reducing analytics endpoint latency ~4×
  SQLAlchemy AsyncSession prevents thread-blocking on DB operations
  Redis client (aioredis) is also non-blocking

5.4 CHOSEN TECH STACK RATIONALE
---------------------------------

  FastAPI vs Django/Flask:
    FastAPI chosen for: async-native, automatic OpenAPI docs, Pydantic validation,
    10x throughput vs sync Django for IO-bound workloads, type hints throughout.
    Django REST too heavy for microservice-style API. Flask lacks async and typing.

  React vs Vue/Angular:
    React chosen for: largest ecosystem, Vite build tooling, shadcn/ui component
    library (unstyled, fully customizable), team familiarity.

  PostgreSQL vs MySQL/MongoDB:
    PostgreSQL for: JSONB (flexible schema for context_data/scenarios),
    UUID support, GIN indexes, pg_trgm for fuzzy text search,
    async driver (asyncpg). MongoDB would lose relational integrity.

  faster-whisper vs OpenAI Whisper API:
    Local deployment = zero per-request API cost, no data privacy issues
    (farmer voice data stays on-premise). faster-whisper uses CTranslate2
    int8 quantization: 2x faster than original Whisper with minimal WER increase.
    Trade-off: requires GPU/CPU resources; model size is 1.5 GB (large-v3).

  Redis vs in-memory cache:
    Redis survives backend restarts; shared across multiple backend instances
    for horizontal scaling. In-memory cache would be lost on container restart.

  Sarvam 30B vs OpenAI GPT-4/Claude:
    Cost: Sarvam is significantly cheaper for Indian use cases.
    Quality: Trained on Indian languages and agricultural context natively.
    Compliance: Data stays within Indian infrastructure (data sovereignty).
    Trade-off: Less capable for complex multi-turn reasoning vs GPT-4.

5.5 SCALABILITY
-----------------
  HORIZONTAL: Stateless FastAPI + JWT (no server-side session) → spin up multiple
  backend containers behind Nginx load balancer.
  DATABASE: PostgreSQL connection pooling via pgbouncer (referenced in main.py
  Supabase startup logic). Supabase handles this automatically.
  CACHING: Redis caches session state; api.js caches analytics for 60s
  client-side to reduce DB load.
  ASYNC I/O: async SQLAlchemy + asyncpg means a single backend process handles
  hundreds of concurrent connections without thread exhaustion.

5.6 SECURITY
--------------
  - JWT: HS256, 60-min access + 7-day refresh tokens
  - Passwords: bcrypt (adaptive cost factor, salted)
  - Rate limiting: slowapi 200/minute default, 10/minute on auth endpoints
  - CORS: explicit origin whitelist (no wildcard in production)
  - SQL injection: impossible via SQLAlchemy ORM parameterized queries
  - JSONB storage: Python dict → SQLAlchemy JSON → psycopg2 properly escaped
  - Input validation: Pydantic models reject malformed input before route logic
  - Audio: temp file deleted in finally block; no persistent storage of voice data
  - Secrets: all in .env, never committed; pydantic-settings loads at runtime

5.7 LIMITATIONS
----------------
  1. IRR is approximated (bisection), not exact. For very irregular cash flows
     (e.g., seasonal aquaponics), a proper Newton-Raphson or polynomial solver
     would be more accurate.
  2. No real-time market price integration: market prices in the land module
     rely on cached data or manual input; live APMC/eNAM API integration pending.
  3. STT is English-only: faster-whisper supports other languages but the domain
     normalization rules are English-specific. Hindi/Marathi support would
     require additional vocabulary mapping.
  4. No multi-tenancy for organizations: each user is independent; no concept of
     a cooperative or organization managing multiple farmers.
  5. Financial model is simplified: no tax model, depreciation schedule, or
     working capital requirement. Suitable for planning but not audited accounts.
  6. Sarvam AI is stateless: no conversation history stored between AI Advisor
     turns (Phase 1 limitation). Each question starts a fresh context window.

SECTION 6 — MENTOR/REVIEWER QUESTIONS AND ANSWERS
================================================================================

Q1: "Why did you choose FastAPI over Django REST Framework?"
A: FastAPI is async-native (all I/O operations non-blocking), has built-in
   OpenAPI documentation generation, and uses Pydantic for type-safe validation.
   For an API that does a lot of I/O — database reads, LLM API calls, audio
   transcription — async matters. Django REST's synchronous ORM would block the
   event loop unless run in threads, adding complexity. Benchmarks show FastAPI
   handles 10-50x more concurrent requests vs sync Django for I/O-bound workloads.

Q2: "Why PostgreSQL and not MongoDB for storing flexible JSON data?"
A: Two reasons. First, the core data (users, farms, sessions, financial_plans)
   is relational with clear FK relationships — forcing this into MongoDB would
   lose referential integrity and cascade delete behavior. Second, PostgreSQL's
   JSONB is a hybrid: the context_data and scenarios columns store flexible JSON
   while remaining queryable via GIN indexes and JSON operators. We get the best
   of both worlds.

Q3: "Explain how NPV and IRR are computed. Why these metrics?"
A: NPV discounts future cash flows to today's value using an 8% annual discount
   rate (reflecting Indian agricultural opportunity cost). NPV > 0 means the
   investment beats the alternative use of capital. IRR is the rate that makes
   NPV = 0 — if IRR > 8%, the project beats the benchmark. Since there's no
   closed-form solution for IRR, we use bisection search over 200 iterations
   converging to 0.01 rupee precision. These metrics are what NABARD and SBI
   loan officers request in business plans, making the output directly useful.

Q4: "How does your STT handle domain-specific agricultural terms?"
A: Three-layer approach. Layer 1: faster-whisper with initial_prompt that gives
   the model context about what domain we're in (aquaponics vocabulary). Layer 2:
   Post-processing with a domain replacement dictionary (30+ regex patterns) that
   maps phonetically similar Whisper outputs to canonical terms — "talapia" →
   "tilapia", "empty/n f t" → "nft". Layer 3: The dual-attempt strategy for
   critical fields like farm_name, using a more constrained decode on retry.

Q5: "What happens if the STT transcription is wrong?"
A: The system provides three safety nets. First, confidence score is shown to the
   user — below the threshold (configurable, default 0.45 for STT, 0.65 for
   entity extraction), a "needs_confirmation" flag appears and alternatives are
   offered. Second, every answer field is editable in the UI before submission.
   Third, the /session/back endpoint lets users roll back and re-answer any
   question. The voice audit log (JSONL) records every attempt for offline
   debugging.

Q6: "Why faster-whisper instead of using the OpenAI Whisper API?"
A: Four reasons: (1) Cost — 0 marginal cost per transcription vs $0.006/minute
   for OpenAI API; for thousands of surveys this adds up significantly. (2)
   Privacy — farmer voice data stays on the server, not processed by a third-
   party service. (3) Latency — local inference is faster than a round-trip to
   OpenAI servers for short utterances (<10 seconds). (4) Offline capability —
   system works without internet for the STT component. Trade-off: we manage the
   hardware (CPU/GPU) and model files ourselves.

Q7: "How does the questionnaire skip logic work?"
A: Each Question object can carry a follow_up_condition dict: {"if": "key == value"}.
   The engine's _eval_condition() method evaluates this mini-expression against
   the current context["answers"] before deciding to skip. For example,
   water_ph is only asked if has_iot_sensors is False — if the farmer already has
   automated sensors, we skip the manual pH entry. This is a deliberate design to
   avoid asking irrelevant questions. Only one condition format is supported
   (key == value) to avoid eval() security risks — the parser uses regex, not
   eval().

Q8: "What is the JSONB context_data design and why deep copy it?"
A: context_data is a JSON column in PostgreSQL that accumulates session state.
   It stores {"answered": [...], "answers": {...}, "crop_intelligence": {...}}.
   SQLAlchemy tracks ORM changes by comparing object identity — if we mutate the
   existing dict in place, SQLAlchemy doesn't detect the change (it sees the same
   object). By doing `context = deepcopy(sess.context_data)`, we create a new
   dict, modify it, and assign `sess.context_data = context`. This triggers
   SQLAlchemy's dirty detection and the UPDATE is issued. This is a subtle but
   critical correctness requirement.

Q9: "How does the three-scenario financial analysis work? What are the factors?"
A: The FinancialCalculator.compute() takes a scenario_factor parameter applied
   only to the revenue side. Base=1.0 (no change), Pessimistic=0.75 (25% revenue
   drop — models a disease outbreak, price crash, or market disruption),
   Optimistic=1.30 (30% uplift — models value-added channels like restaurant
   supply or direct-to-consumer). Costs remain constant across scenarios (OPEX
   is relatively fixed in the short term). This matches how NABARD and DFIs
   structure sensitivity analysis in agricultural project reports.

Q10: "How is the recommendation engine implemented? Is it ML/AI?"
A: Purely rule-based — 15+ deterministic if-else rules derived from aquaponics
   best practices literature and agricultural economics. For example: if feed cost
   > 45% of total OPEX, fire a "high feed cost" recommendation with specific
   actionables (bulk purchasing, FCR tracking, duckweed supplementation). No ML
   because: (1) ground truth labeled data for aquaponics is scarce in India;
   (2) rules are interpretable and defensible to farmers and reviewers; (3) zero
   inference cost; (4) deterministic output for auditing. The Sarvam LLM is used
   only for open-ended conversational advice, not for financial recommendations.

Q11: "How does the Land Farm module differ from the Aquaponics module?"
A: Three key differences. Architecture: context_data["module"] = "land_farm_voice"
   acts as a routing flag used throughout the backend (report.py, analytics,
   AI advisor). Question bank: land survey asks about crop types/area/yield/MSP
   awareness instead of fish tanks/stocking density/water chemistry.
   Financial model: land_financial_service.py computes per-crop P&L (revenue =
   yield × market_price × cycles) vs the CAPEX/OPEX/ROI model of aquaponics.

Q12: "How does the PDF report get generated? What library?"
A: ReportLab (Canvas API). The _render_pdf() function creates an A4 canvas,
   writes text sections using drawString() with precise x,y coordinates.
   Dynamic pagination kicks in when y < 70 pixels: showPage() starts a new page.
   The entire PDF is generated in a BytesIO buffer (in-memory), never touches
   disk. The report has four sections: financial summary, survey inputs, crop
   feasibility analysis, and AI recommendations. StreamingResponse sends the
   bytes directly to the browser with Content-Disposition: attachment.

Q13: "How is data validated before it reaches your business logic?"
A: Three layers. Layer 1: Pydantic models on request bodies (FastAPI validates
   at the HTTP boundary — wrong type → 422 immediately). Layer 2:
   QuestionnaireEngine.parse_answer() validates against question-specific rules
   (min/max for numbers, fuzzy match for select, yes/no for boolean). Layer 3:
   SQLAlchemy column types (Float, Integer, String) enforce DB-level constraints.
   For voice input, normalize_number_transcript() converts words to digits before
   validation so "fifty" passes the min_value check.

Q14: "What happens if the database goes down?"
A: The main.py startup is fault-tolerant. _init_db() retries with exponential
   backoff (2^attempt seconds: 2s, 4s, 8s). If all attempts fail, the backend
   STARTS ANYWAY and logs an error. This is intentional — the /health endpoint
   reports {"status": "degraded", "db": "error"} rather than the container
   crash-looping (which would prevent load balancer health checks from ever
   passing). DB-dependent routes return 503 with the db_connection_error_handler.

Q15: "How does the IoT integration work? What sensors are supported?"
A: POST /api/v1/iot/ingest accepts readings for: pH, dissolved_oxygen_mg_l,
   temperature_c, ammonia_mg_l, nitrite_mg_l, nitrate_mg_l, turbidity_ntu,
   tds_ppm. IoT devices auto-register on first ingestion using a
   farm_id + device_uid unique constraint. The reading is timestamped and stored
   in water_readings table (indexed by timestamp for time-range queries).
   The analytics module aggregates these into daily averages for trend charts.
   Currently data push-only; future work would add threshold alerts.

Q16: "How does authentication work across frontend and backend?"
A: After login, the backend returns access_token (60 min) and refresh_token
   (7 days). Frontend stores both in localStorage. The Axios instance in api.js
   adds Authorization: Bearer <access_token> to every request via an interceptor.
   On a 401 response, the interceptor attempts to use the refresh_token to get a
   new access_token. If refresh also fails (token expired/revoked), the user is
   logged out. JWTs contain user_id as the "sub" claim; get_current_user() decodes
   and validates, returning the User ORM object.

Q17: "What is your rate limiting strategy?"
A: slowapi (Python port of Flask-Limiter) is integrated as ASGI middleware.
   Default limit: 200 requests/minute per IP. Auth endpoints (/auth/login,
   /auth/register): 10/minute to prevent brute-force attacks. The limit is stored
   in memory (no Redis required for single-instance; can switch to Redis backend
   for distributed deployment). Exceeded limit returns 429 Too Many Requests.

Q18: "How do you handle concurrent users accessing the same data?"
A: SQLAlchemy AsyncSession uses connection pooling (asyncpg). Each request gets
   its own session (via Depends(get_db) dependency). Session.flush() writes to DB
   within the transaction but does not commit — FastAPI's get_db() dependency
   commits on successful response and rolls back on exception. Concurrent writes
   to the same session_id are prevented by the user_id ownership check.

Q19: "Why Sarvam LLM and not GPT-4 for the AI Advisor?"
A: Sarvam 30B is specialized for Indian languages, agricultural context, and uses
   Indian financial conventions (₹, lakh, crore) natively. It's significantly
   cheaper to run. For Phase 1 (stateless advice), the quality is sufficient.
   GPT-4 would be preferred for complex multi-turn reasoning but at 20-100x cost.
   The system is LLM-agnostic (the settings.py has ANTHROPIC_API_KEY and
   OPENAI_API_KEY placeholders), so switching providers requires only changing
   the SarvamLLMService HTTP call.

Q20: "What are your biggest security concerns?"
A: Four main concerns: (1) JWT secret key — must be high entropy (32+ hex chars)
   and rotated periodically. If compromised, all tokens are forgeable. Mitigated
   by short 60-min access token lifetime. (2) Audio data — voice recordings could
   contain sensitive information. Mitigated by deleting temp files immediately in
   the finally block. (3) CORS — production must use the explicit origin whitelist,
   not a wildcard. (4) The AI Advisor receives farmer financial data as part of
   the prompt — when using third-party LLMs (GPT-4), this data leaves the system.
   Sarvam mitigates this somewhat, but for production, PII scrubbing of the
   system prompt would be needed.

Q21: "How would this scale to 10,000 concurrent farmers?"
A: Current architecture supports this with: (1) Horizontal backend scaling behind
   Nginx load balancer — multiple FastAPI containers (stateless). (2) PostgreSQL
   connection pooling via pgbouncer / Supabase pooler (already referenced in code).
   (3) Redis caching for session state. (4) Client-side 60s analytics cache in
   api.js to reduce DB aggregation queries. (5) faster-whisper on GPU nodes (can
   process 50+ transcriptions/minute per GPU). Estimated cost at 10k users/day:
   ~2-3 Supabase Pro plan instances + 2 GPU VMs for Whisper.

Q22: "What is the WER evaluation module for?"
A: WER (Word Error Rate) is the standard metric for STT quality evaluation:
   WER = (Substitutions + Deletions + Insertions) / Total Reference Words.
   A WER of 0.05 means 95% accuracy. The eval module lets us A/B test faster-
   whisper vs browser Web Speech API on the same agricultural vocabulary test set.
   We expect faster-whisper with domain prompting to outperform browser STT on
   specialist terms like "barramundi", "NFT", "DWC" by ~30% WER reduction.
   This is enabled via EVAL_MODE=true env var (disabled in production).

Q23: "What happens if the crop knowledge base has an unknown crop?"
A: evaluate_crop() checks self._index.get(name.lower()). On None, it returns:
   {feasibility: "unknown", reasons: ["Crop 'X' not found in knowledge base"],
    suggestions: [list of all known crops]}. This graceful degradation means the
    survey completes successfully even for exotic/regional crops not in the KB.
    The KB can be extended by adding entries to crop_knowledge_base.json.

Q24: "Why did you choose JSONB for scenarios storage instead of normalized tables?"
A: The three scenarios each contain 30+ metrics plus a month-by-month cash flow
   array (up to 60 entries × 5 fields each). Normalizing this into relational
   tables would require 3+ additional tables with hundreds of rows per plan.
   JSONB stores the entire nested structure in one column, with no query
   complexity for read operations (a single SELECT returns everything). GIN
   indexing enables JSON path queries when needed. The trade-off is that JSONB
   is less queryable for analytics than normalized tables, but analytics (report.py)
   already operates at the FinancialPlan level, not the individual scenario level.

Q25: "How does the system perform under poor network conditions?"
A: Three considerations. (1) GZip middleware compresses API responses >1000 bytes,
   reducing bandwidth by 60-80% for JSON responses. (2) Partial session state:
   if a network failure occurs mid-survey, the context_data up to the last
   submitted answer is persisted in DB; the user can resume via GET /session/{id}.
   (3) Client-side 60s analytics cache avoids repeated round-trips.
   Known gap: no offline-first PWA capability (future work).

8.1 CROSS-QUESTIONS AND FOLLOW-UPS

Mentor: "You said deepcopy is needed for SQLAlchemy — can you prove it?"
Answer: Yes. SQLAlchemy's Unit of Work pattern tracks "dirty" objects by comparing
the current attribute value to the last flushed value using Python identity checks
(is vs ==) for mutable objects like dicts. If you modify the existing dict in-place,
the attribute reference hasn't changed (same object id), so SQLAlchemy doesn't mark
the column as dirty. Reassigning `sess.context_data = new_dict` triggers the
attribute event listener that marks the instance as modified. This is documented in
SQLAlchemy's "mutable column types" section and is a common production bug.

Mentor: "How accurate is your bisection IRR? Could it be wrong?"
Answer: Bisection converges to within ±0.01 rupee NPV tolerance after 200
iterations, which translates to IRR precision of approximately ±0.1%. For
practical farming decisions (comparing IRR of 18% vs 12%), this is sufficient.
The theoretical risk is non-convergence if multiple sign changes exist in the
NPV curve (multiple IRRs) — this can happen with non-conventional cash flows
(large mid-period costs). Our cash flow model is conventional (one large initial
outflow, then positive monthly flows), so a single IRR always exists.

Mentor: "What's the difference between gross profit and net profit in your model?"
Answer: In our simplified model, gross_profit = annual_revenue - annual_opex, and
net_profit = gross_profit. We do NOT model taxes, depreciation, or amortization.
This is explicitly noted as a limitation (Section 5.7). For a 10-minute farmer
survey, adding tax modeling would require asking 8-10 additional questions
(depreciation method, tax slab, loan interest) that are beyond scope and would
reduce survey completion rates. The output is labeled as a "projection" not a
"financial statement."

Mentor: "Why not use Alembic for database migrations?"
Answer: Alembic is valuable for production systems with frequent schema evolution.
At this stage, infra/schema.sql provides a clean, readable, version-controlled
schema definition. The trade-off: adding a new column requires manually editing
schema.sql and running it against the DB, rather than generating a migration file.
For a student project with 1-2 contributors and infrequent schema changes, this
is acceptable. In a production deployment with a team, Alembic would be added.

Mentor: "Could two users corrupt each other's session data?"
Answer: No, by design. Every database query that retrieves a session includes
`Session.user_id == current_user.id` in the WHERE clause. _get_session_or_404()
is used by every session endpoint. Even if a malicious user guessed a valid
session UUID, the query returns 404 because their user_id doesn't match. UUIDs
also have 2^122 bits of entropy — collision probability is negligible.

Mentor: "How would you add Hindi language support?"
Answer: Three components need change: (1) faster-whisper already supports Hindi
natively (set language="hi" in the transcribe call). (2) The DOMAIN_REPLACEMENTS
list in voice_interpretation.py would need Hindi phonetic variants (e.g.,
"टिलापिया" or Hindi homophones). (3) The QuestionnaireEngine questions would
need translations. The API is language-agnostic (passes language param to Whisper).
Frontend would need i18n (react-i18next). This is 2-3 weeks of work.

SECTION 9 — WEAK POINTS AND RISK AREAS
================================================================================

RISK 1: "No real-time market prices"
Challenge: Land module uses static/manual price inputs
Defense: Current scope validates the financial model architecture. Live APMC/eNAM
API integration is planned as Phase 2. The land_market_price_service.py file
already has the service structure for this integration — the plumbing exists,
only the external API key is missing.

RISK 2: "STT accuracy not measured quantitatively in this version"
Challenge: No benchmark WER number to cite
Defense: The eval framework (eval/run_wer_eval.py, EVAL_MODE) is built and
designed for this measurement. We chose domain post-processing over raw STT
accuracy because even a 90% accurate STT transcript without domain normalization
produces nonsensical structured answers (farm_species = "telepathy" instead of
"tilapia"). The normalization layer is more valuable than raw WER improvement.

RISK 3: "Financial model doesn't include taxes or depreciation"
Challenge: Not a complete financial model
Defense: Acknowledged explicitly as a simplification. The target user is a farmer
deciding whether to invest ₹2 lakh in a system, not a CA preparing audited
accounts. NABARD project reports for small farmers also use simplified P&L models.
Adding taxes would require asking 8+ more survey questions, harming completion rates.

RISK 4: "Sarvam AI is stateless (no conversation history)"
Challenge: AI advisor cannot reference previous turns
Defense: This is a Phase 1 constraint documented in the codebase. The system
prompt provides full farm context on every call. For simple Q&A ("Is my ROI
good? What should I do about feed costs?"), single-turn is sufficient. Multi-turn
history would require a conversation store (Redis or DB) — the architecture
supports adding this in Phase 2.

RISK 5: "No automated E2E tests"
Challenge: Testing relies on unit tests (services) + manual testing
Defense: Unit tests cover all financial calculations (test_financial_service.py),
voice interpretation (test_voice_interpretation.py), crop intelligence
(test_crop_intelligence.py), and land financial (test_land_financial_service.py).
The FastAPI TestClient is used in test_auth.py. E2E tests require a running DB
(pytest -k "not Endpoint" skips these). Coverage is focused on the financial
calculation core (the highest-risk, most complex logic).

RISK 6: "Google Sheets sync requires service account credentials"
Challenge: Setup complexity for farmers
Defense: This is an administrator/operator setup step, not a farmer step. The
farmer never sees the Google service account. The sync is an optional export
feature; the core platform (survey → financial plan → PDF) works without it.
